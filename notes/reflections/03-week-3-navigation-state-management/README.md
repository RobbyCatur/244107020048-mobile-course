# Refleksi Minggu 3

## 1. Kapan setState masih cukup, dan kapan state harus naik ke Riverpod?
`setState` cukup selama data hanya hidup di satu widget dan tidak ada pihak lain yang butuh membaca atau mengubahnya, misalnya status animasi atau isi sebuah `TextEditingController`. Masalah muncul ketika state harus dibagi ke beberapa cabang pohon widget atau logikanya perlu diuji tanpa widget. Di titik itu state lebih baik naik ke Riverpod: `TodoListNotifier` memisahkan data tugas dari `TodoPage`, sehingga daftar, filter, dan halaman statistik bisa membaca sumber kebenaran yang sama. Keuntungan lain, notifier tetap berisi ketika berpindah halaman dan perilakunya dapat diuji lewat `ProviderContainer` tanpa `pumpWidget`.

## 2. Apa perbedaan context.go dan context.push, dan kapan masing-masing tepat digunakan?
`context.push` menumpuk rute baru di atas stack sehingga tombol kembali mengembalikan pengguna ke halaman sebelumnya, cocok untuk detail atau dialog penuh seperti membuka `ProductPage` dari daftar tugas. `context.go` mengganti posisi navigasi, bukan menumpuk, sehingga halaman lama digantikan; ini tepat untuk berpindah tab pada `NavigationBar`, misalnya `context.go('/stats')` saat memilih tab statistik agar stack tidak membengkak setiap kali berpindah tab. Karena halaman statistik merupakan tujuan utama, memakai `push` di sana justru membuat tombol back terasa aneh.

## 3. Bagaimana AsyncValue mencegah bug dibanding tiga boolean terpisah?
Tiga flag `isLoading`, `isError`, dan `hasValue` bisa berada dalam kombinasi yang mustahil, misalnya kosong sekaligus error, atau error sekaligus memegang data basi, dan tiap jalur UI harus menjaga ketiganya tetap sinkron. `AsyncValue` memadatkan kemungkinan itu menjadi satu state yang saling eksklusif: `AsyncLoading`, `AsyncError`, atau `AsyncData`. `when()` memaksa ketiga cabang ditangani saat build; meninggalkan salah satunya adalah error kompilasi, bukan bug runtime yang baru terlihat di lapangan. Pada `StatsPage`, tombol retry cukup memanggil `ref.invalidate` karena framework yang mengembalikan state ke loading.

## 4. Bagian mana dari hasil AI yang Anda perbaiki, dan mengapa?
Hasil AI untuk `StatsPage` sudah benar soal pemisahan notifier dan `when()`, tetapi punya dua celah. Pertama, `Random()` dan jeda 2 detik ditulis langsung di dalam `build()`, sehingga unit test akan lambat dan tidak deterministik; saya ubah keduanya menjadi getter `latency`, `failureRate`, dan `random` agar test bisa menurunkannya tanpa menyentuh kode produksi. Kedua, percobaan awal memakai `expectLater(container.read(statsProvider.future), throwsA(...))` yang menggantung sampai timeout di Riverpod 3; saya ganti dengan membaca state setelah `pumpEventQueue()` dan memeriksa `hasError`. Saya juga memangkas duplikasi `TodoTile` dari `TodoPage`, memisahkannya ke widget sendiri agar mudah diuji.
